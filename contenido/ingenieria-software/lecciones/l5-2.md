## Kanban: gestión visual del flujo

Método ágil basado en un **tablero visual** y **límites WIP** (Work In Progress) para gestionar el flujo de trabajo. {a Apuntes de Ingeniería de Software · Unidad 5}

```mermaid Tablero Kanban básico
flowchart LR
  Backlog[Backlog<br/>Priorizado] --> ToDo[To Do<br/>Listo para empezar]
  ToDo --> Doing[Doing<br/>En progreso (WIP límite)]
  Doing --> Review[Review<br/>En revisión/QA]
  Review --> Done[Done<br/>Completado (DoD)]
```


## Principios clave

| Principio | Qué significa |
|---|---|
| **Visualizar el flujo** | Tablero con columnas: cada tarjeta = ítem de trabajo. |
| **Limitar WIP** | Límite máx. de ítems en "Doing" / "Review"; evita multitarea, expone cuellos de botella. |
| **Gestionar el flujo** | Métricas: *lead time*, *cycle time*, *throughput*; optimizar flujo, no utilización. |
| **Políticas explícitas** | Reglas claras: cuándo mover tarjeta, qué significa "Done", quién puede mover. |
| **Mejorar continuamente** | *Kaizen*: retrospectivas, experimentos, métricas. | {a Apuntes de Ingeniería de Software · Unidad 5}

## WIP Limits: por qué funcionan

- **Ley de Little**: *Cycle Time = WIP / Throughput*. Reducir WIP → reduce *cycle time*.
- Evita *context switching* (costo cognitivo de cambiar de tarea).
- Hace visibles los cuellos de botella: si columna "Review" se llena → falta revisores. {a Apuntes de Ingeniería de Software · Unidad 5}

## JIRA: herramienta de gestión de proyectos

Herramienta *leader* para gestión ágil: issues, boards (Scrum/Kanban), sprints, reportes, *roadmaps*, automatizaciones. {a Apuntes de Ingeniería de Software · Unidad 5}

| Función | Qué hace |
|---|---|
| **Issues** | Unidades de trabajo: *Story*, *Task*, *Bug*, *Epic*, *Spike*. Campos: resumen, descripción, prioridad, *assignee*, *labels*, *story points*, *sprint*. |
| **Boards** | *Scrum Board* (con sprints) o *Kanban Board* (flujo continuo). Columnas personalizables, *quick filters*, *swimlanes*. |
| **Sprints** | Crear, planificar, *start/end*, *burndown chart*, *velocity chart*. |
| **Reportes** | *Burndown*, *velocity*, *control chart* (cycle time), *cumulative flow diagram*. |
| **Automatizaciones** | Reglas: "Si issue movido a Done → transición automática", "Si prioridad Alta → asignar a lead". |
| **Integraciones** | GitHub/GitLab/Bitbucket (commits/PRs enlazados), Confluence, Slack, Teams. | {a Apuntes de Ingeniería de Software · Unidad 5}

## Scrum vs. Kanban vs. Scrumban

| Aspecto | **Scrum** | **Kanban** | **Scrumban** |
|---|---|---|---|
| **Cadencia** | Sprints fijos (1-4 sem) | Flujo continuo (sin sprints) | Sprints opcionales / cadencia híbrida |
| **Planificación** | Sprint Planning al inicio | Continua / *on demand* | Híbrida: planificación por hitos + flujo |
| **Roles** | PO, SM, Dev Team definidos | No roles obligatorios | Flexible: puede tener PO/SM |
| **WIP Limits** | No obligatorios (pero recomendados) | **Obligatorios** (core) | Obligatorios |
| **Entregas** | Al final de cada Sprint | Continuas / *on demand* | Continuas o por hitos |
| **Métricas clave** | *Velocity*, *burndown* | *Lead time*, *cycle time*, *CFD* | Híbridas |
| **Ideal para** | Equipos nuevos, alcance definido, ritmos fijos | Mantenimiento, soporte, flujo continuo, equipos maduros | Transición Scrum→Kanban, equipos mixtos, mantenimiento + features | {a Apuntes de Ingeniería de Software · Unidad 5}

- Kanban: visualizar flujo, limitar WIP, gestionar flujo, políticas explícitas, mejora continua.
- JIRA: issues (Story/Task/Bug/Epic), boards Scrum/Kanban, sprints, reportes, automatizaciones.
- Scrum = sprints fijos, roles definidos, velocity. Kanban = flujo continuo, WIP limits, lead time. Scrumban = híbrido flexible. {a Apuntes de Ingeniería de Software · Unidad 5}
