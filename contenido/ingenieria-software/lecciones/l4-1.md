La **implementación** es la fase donde se traduce el diseño previo a código ejecutable y bases de datos. Solo corresponde iniciarla después de un análisis exhaustivo de requisitos y de aplicar principios de diseño. {a Apuntes de Ingeniería de Software · Unidad 4}

## Selección de herramientas

Depende de las decisiones tomadas en diseño y del entorno donde el sistema operará. {a Apuntes de Ingeniería de Software · Unidad 4}

| Categoría | Opciones típicas | Criterio de elección |
|---|---|---|
| **IDEs** | Visual Studio, Eclipse, IntelliJ IDEA, VS Code | Lenguaje, ecosistema, *plugins*, equipo |
| **Lenguajes** | Python, Java, C++, JavaScript, C#, Go, Rust | Tipo de sistema, rendimiento, ecosistema, equipo |
| **DBMS** | MySQL, PostgreSQL, SQL Server, MongoDB, Redis | Modelo de datos, escalabilidad, consistencia, equipo |
| **Control de versiones** | Git (GitHub, GitLab, Bitbucket) | Estándar de facto |
| **CI/CD** | GitHub Actions, GitLab CI, Jenkins, CircleCI | Integración con repo, facilidad, costo | {a Apuntes de Ingeniería de Software · Unidad 4}

## Implementación ágil

La fase se divide en ciclos cortos llamados **sprints** (1-4 semanas), con entrega incremental y adaptación continua. {a Apuntes de Ingeniería de Software · Unidad 4}

## Clean Code (código limpio)

Prácticas para que el código sea funcional, sostenible y fácil de mantener. {a Apuntes de Ingeniería de Software · Unidad 4}

| Principio | Qué significa |
|---|---|
| **Nombres reveladores** | Variables, funciones, clases con nombres que explican *qué* y *por qué* |
| **Funciones pequeñas** | Una función = una responsabilidad (< 20 líneas ideal) |
| **DRY** | *Don't Repeat Yourself*: no duplicar lógica; abstraer |
| **KISS** | *Keep It Simple, Stupid*: evitar complejidad innecesaria |
| **YAGNI** | *You Aren't Gonna Need It*: no implementar "por si acaso" |
| **Comentarios necesarios** | Solo para *por qué*, no *qué* (el código dice el *qué*) |
| **Formato consistente** | Sangría, espacios, llaves, *linting* automático |
| **Manejo de errores** | Excepciones significativas, *fail fast*, *clean up* (finally/try-with-resources) | {a Apuntes de Ingeniería de Software · Unidad 4}

> **Regla**: el código se lee más veces de las que se escribe. Optimizar para lectura. {d}

## Revisión técnica (Code Review)

Inspección del código por pares **antes** de mergear. Detecta defectos temprano, comparte conocimiento, mantiene estándares. {a Apuntes de Ingeniería de Software · Unidad 4}

| Tipo | Qué revisa |
|---|---|
| **Formal (Fagan)** | Proceso estructurado: preparación, reunión, rework, seguimiento |
| **Ligera (*Lightweight*)** | *Pull request*, *pair programming*, *over-the-shoulder* |
| **Automatizada** | *Linters*, *static analysis* (SonarQube, CodeQL), *security scanning* | {a Apuntes de Ingeniería de Software · Unidad 4}

> **Regla**: revisar **antes** de mergear a *main*. *Pair programming* = revisión continua. {d}

- Revisión técnica: antes de merge; *pull request*, *pair programming*, *linters*, *static analysis*. {a Apuntes de Ingeniería de Software · Unidad 4}
